## Cosa è Varco

Un servizio privato di file transfer stile WeTransfer, self-hosted su Cloudflare + Backblaze B2. Serve a mandare file di qualsiasi tipo e dimensione a persone specifiche tramite link con password.

**Generico per definizione**: nessuna logica specifica per estensione o tipo MIME. Foto, video, archivi, documenti, qualsiasi cosa. Non implementare validazione o categorizzazione per formato.

Due modi di caricare:
- **Utenti fissi** — io e poche persone di fiducia, whitelist email permanente
- **Invitati a tempo** — link di upload monouso/limitato che genero io e che scade da solo

Un solo modo di scaricare: link + password, nessun account richiesto per chi riceve.

| Router | **Hono** |

## Vincoli architetturali (VINCOLANTE — sono il cuore del progetto)

### 1. Upload: presigned PUT, il file non tocca mai il Worker

Il Worker genera solo un presigned PUT url S3 v4 verso B2. Il browser carica direttamente su B2.

Motivo: bypassa il limite di 100MB sul request body del piano Cloudflare Free, e azzera il CPU time del Worker sull'upload.

**Single PUT, niente multipart** — B2 accetta fino a 5GB in una singola PUT, sufficiente. Non implementare multipart.

### 2. Download: proxy in streaming, mai un redirect

Il Worker fa `fetch()` verso B2 e restituisce `response.body` al client come `ReadableStream` pass-through. Mai bufferizzare il file in memoria, mai `arrayBuffer()`.

Motivo: l'egress B2 → Cloudflare è gratuito (Bandwidth Alliance). Un redirect a un presigned GET farebbe uscire i dati da B2 verso il client, a pagamento. Lo streaming pass-through non consuma CPU proporzionale alla dimensione: l'attesa su I/O non conta come CPU time.

### 3. Password generate dal sistema, hash SHA-256 singolo

La password NON la sceglie l'utente: la genera il Worker, alta entropia (12 caratteri crypto-random, oppure 4 parole da wordlist).

Con entropia ~64 bit il brute force è infeasibile a prescindere dalla lentezza dell'hash, quindi **un singolo SHA-256 con salt è sufficiente**.

**NON usare PBKDF2/bcrypt/scrypt**: costerebbero 50-100ms di CPU per download, sfondando il limite di 10ms del piano free. SHA-256 costa ~0.01ms. Il rallentamento dell'hash serve a proteggere password deboli scelte da umani — problema che qui non esiste per costruzione.

### 4. Budget CPU: restare sotto i 10ms per richiesta

Ogni scelta implementativa deve rispettare questo. Niente librerie pesanti, niente lavoro sincrono inutile, niente parsing di payload grandi.

## Endpoint

### `POST /api/upload`

Endpoint **unico** di upload. Accetta due forme di autorizzazione:
- Header `Cf-Access-Authenticated-User-Email` presente → utente fisso, autorizzato da Cloudflare Access a monte. Il Worker si fida (verifica solo la presenza dell'header, l'auth vera è già avvenuta).
- Query param `?invite={token}` → valida `invite:{token}` in KV; se assente/scaduto → 403. Decrementa `remainingFiles`, errore se esaurito.

Se nessuna delle due → 403.

Input: `{ filename, size, expiresInDays, maxDownloads? }`

Azioni:
1. Genera `fileId` (crypto-random) e `token` per il link di download
2. Genera password random ad alta entropia
3. Calcola `salt` random + `hash = SHA-256(salt + password)`
4. Genera presigned PUT verso B2, key: `f/{YYYY}/{MM}/{fileId}/{filename}`
5. Scrive KV `file:{token}` con `expirationTtl` allineato a `expiresInDays`:
   ```
   { fileId, key, filename, size, uploaderEmail | inviteToken,
     hash, salt, expiresAt, maxDownloads, downloadCount: 0 }
   ```

Ritorna: `{ uploadUrl, downloadUrl: "/d/{token}", password }`

La password viene mostrata all'uploader **una sola volta** nella UI, con pulsante copia. Non è più recuperabile dopo (non è salvata in chiaro).

### `GET /d/:token`

Serve la pagina con form password. **Nessuna informazione sul file prima dell'autenticazione** — né nome, né dimensione, né data. Se il token non esiste rispondi con la stessa pagina generica (non rivelare l'esistenza o meno del token).

### `POST /d/:token`

Body: `{ password }`
1. Legge `file:{token}` da KV → 404 generico se assente
2. `SHA-256(salt + password)` confrontato con `hash` in **tempo costante**
3. Password errata → incrementa `fail:{token}` in KV (TTL 1h); a 5 tentativi → 429 con blocco temporaneo
4. Scaduto o `downloadCount >= maxDownloads` → 410 Gone
5. OK → `fetch()` da B2, restituisci `response.body` in streaming con header `Content-Disposition: attachment` e `Content-Length` corretto
6. Incrementa `downloadCount` (usa `ctx.waitUntil()` per non ritardare la risposta)

### `POST /api/invite`

Protetto da Cloudflare Access (solo il mio account).

Input: `{ label, maxFiles, ttlHours }`

Genera token random, scrive `invite:{token}` in KV con `expirationTtl: ttlHours*3600`.

Ritorna link pronto: `/?invite={token}`

### Cron Trigger (giornaliero)

Il TTL di KV elimina da solo i metadata scaduti, ma **non** i file su B2. Il cron:
1. Lista gli oggetti su B2 sotto prefisso `f/`
2. Per ogni oggetto, verifica se esiste ancora la entry KV corrispondente
3. Se non esiste più → `DeleteObject` su B2

Aggiungi anche una **lifecycle rule** su B2 come rete di sicurezza (documentala nel README, non è codice).

## Frontend — priorità assoluta alla semplicità d'uso

**Pagina upload** (`/`):
- Drag & drop + click per selezionare, un campo per la scadenza (default 7 giorni), pulsante upload
- Upload diretto a B2 con `XMLHttpRequest` (serve `upload.onprogress` per la barra di avanzamento — `fetch()` non lo espone)
- A fine upload: mostra link + password con due pulsanti copia, e un pulsante "copia entrambi" che mette in clipboard un testo già pronto da incollare in chat
- Se aperta con `?invite=...`, si comporta identicamente ma passa il token — l'invitato non deve accorgersi di nulla di diverso

**Pagina download** (`/d/:token`):
- Solo campo password e pulsante. Al submit parte il download nativo del browser.

**Pagina admin** (`/admin`):
- Form minimale per generare un invito, output il link da copiare

Design sobrio, mobile-friendly, dark mode via `prefers-color-scheme`. Niente dipendenze CSS esterne.

## Sicurezza

- Mai loggare password o token in chiaro, nemmeno in dev
- Confronto hash in tempo costante
- CORS: solo il dominio del Worker
- Application Key B2 dedicata, permessi limitati al singolo bucket, **mai la master key**
- Bucket B2 privato (`allPrivate`) con SSE-B2 attiva
- Messaggi d'errore generici lato download: non distinguere "token inesistente" da "password errata"
